1. 先背这 15 个结论

1

错误、缺陷、失效

错误属于“人”，缺陷属于“代码（静态）”，失效属于“运行（动态、可观察）”。

2

用例必须有预期输出

没有可判定的期望结果，就无法判断测试是通过还是失败。

3

测试不能证明“没有错误”

测试只能证明缺陷存在；穷尽测试不可能，必须按风险和优先级取舍。

4

两个分类维度别混

静态/动态看“是否运行程序”；黑盒/白盒/灰盒看“是否利用程序内部结构信息”。

5

V 模型配对

需求分析—验收测试；概要设计—系统测试；详细设计—集成测试；编码—单元测试。

6

W 模型改进

开发一个 V、测试一个 V；测试与开发并行，需求、设计等文档也纳入测试对象。

7

逻辑覆盖强弱

语句 → 判定 → 条件 → 判定/条件 → 条件组合 → 路径（课程口径，由弱到强）。

8

环形复杂度三算法

V(G) = E − N + 2 = 判定节点数 + 1 = 区域数（含图外部区域）。

9

边界值三点

上点、离点、内点。闭区间 [100, 300] 取 100/300、99/301、200。

10

因果图五约束

E 互斥、I 包含、O 唯一、R 要求、M 屏蔽；M 是输出约束。

11

Driver 与 Stub

Driver 模拟上级调用者；Stub 模拟下级被调模块。自顶向下用桩，自底向上用驱动。

12

四种集成策略

大爆炸、自顶向下、自底向上、三明治；选策略看接口稳定性、缺陷定位和桩/驱动成本。

13

三层测试依据

单元测试依据详细设计；集成测试依据概要设计；系统测试依据需求规格说明书。

14

CMM 五级

初始 → 可重复 → 已定义 → 已管理 → 优化；“无序→有管理→标准化→量化→持续改进”。

15

三个必背清单

ISO 9126 六大质量特性；IEEE 829 八类测试文档；整体缺陷清除率 = D1 / D。

1.2 错误、缺陷与失效

概念英文含义例子
错误error人产生的过失行为，属于人的思维或操作错误程序员把 sum = a + b 误写成 sum = a - b
缺陷 / 故障fault / defect错误在软件中留下的具体体现，静态地存在于代码或文档中源代码中的语句 sum = a - b
失效failure程序运行后表现出的、用户可观察到的不符合预期的行为输入 3 和 5，输出 −2 而不是 8
一句话记忆

错误属于“人”，缺陷属于“代码（静态）”，失效属于“运行（动态、可观测）”。人犯 error，在软件中留下 defect，缺陷在特定输入被触发后才表现为 failure。

补充：中文语境中的“故障”有时指缺陷被触发后系统功能异常的状态，是缺陷走向失效的中间表现。做题时按教材用词区分即可。

1.3 软件测试的定义、目的与原则

测试有两种经典定义：一是“验证程序正确”，二是“发现错误”。现代测试更强调后者：测试的目的是尽可能早、尽可能多地发现软件中的缺陷，而不是证明程序没有错误。

必背判断

“软件测试的目的就是证明程序中不存在错误。”——错误。测试只能证明缺陷存在，不能证明缺陷不存在；即使所有用例都通过，也不能说明软件没有缺陷。

软件测试的七条基本原则

  1. 测试显示缺陷存在，但不能证明缺陷不存在。
  2. 穷尽测试是不可能的。输入组合与执行路径数量极其庞大，必须基于风险和优先级取舍。
  3. 测试应尽早介入。缺陷发现得越晚，修复成本越高。
  4. 缺陷集群性（二八原则）。约 80% 的缺陷集中在约 20% 的模块中，资源应向缺陷高发模块倾斜。
  5. 杀虫剂悖论。长期重复使用同一组用例，发现新缺陷的能力会下降，必须定期评审和更新用例。
  6. 测试活动依赖上下文。不同软件、不同阶段、不同风险，测试方法不同。
  7. 不存在缺陷的谬论。软件没有缺陷，也可能不满足用户需求。

1.4 测试用例的构成

要素说明考试注意
用例标识 / 名称唯一编号与简明名称便于追踪和管理
测试项被测功能或模块如“用户登录”
前置条件执行前必须满足的环境或数据状态如“已打开登录页”
输入测试数据、操作用户名、密码等
执行步骤按顺序描述如何操作步骤要可重复
预期输出期望结果 / 判定标准最关键，不能缺
重要级别优先级高 / 中 / 低
参照规范需求或设计依据便于追溯
最易失分

只写了“输入用户名和密码，点击登录”，却没有写“预期输出”，这条用例不完整。必须增加“登录成功，跳转到系统首页并显示当前用户名”等可判定的期望结果。

1.5 测试环境与测试人员

  • 测试环境：硬件、操作系统、网络、数据库、中间件、被测软件、测试工具与测试数据等。环境应尽量接近用户真实使用环境，并保证可重复、可控制。
  • 测试人员：应具备测试方法与工具知识、一定的编程与业务理解能力、严谨细致的工作作风、良好的沟通与文档能力，以及职业道德和保密意识。

1.6 典型例题

例 1某程序员编写“求两数之和”的程序时，把 sum = a + b 误写成 sum = a - b。程序上线后，用户输入 3 和 5，得到 −2 而不是 8，导致结算金额出错。请分别指出人为错误、软件缺陷和失效，并说明三者关系。
查看参考答案与解析
  • 人为错误（error）：程序员把加法误写成减法这一过失行为。
  • 软件缺陷（fault / defect）：源代码中的语句 sum = a - b，是静态存在于代码中的偏差。
  • 失效（failure）：程序运行后输入 3 与 5 却输出 −2，是用户可观察到的、与预期不符的行为。
  • 关系：人犯 error，在软件中留下 defect；缺陷在特定输入条件下被触发，才表现为 failure。

CHAPTER 02

第 2 章 软件开发过程与软件测试

高频模型选择 / 简答V/W 模型必考

2.1 软件开发过程模型

模型核心特点适用场合主要局限
瀑布模型阶段顺序推进，文档驱动，阶段评审需求明确、稳定，项目可控回溯困难，测试介入晚，需求变更成本高
原型模型先做可运行原型，逐步明确需求需求不清晰、用户参与度高原型可能被误当产品，管理不当易失控
螺旋模型迭代 + 风险分析，每圈都做风险评估大型、高风险、复杂项目风险分析需要专业能力，成本较高
增量模型按功能分批开发、分批交付可拆分功能、希望尽早交付需要良好的架构与集成计划
迭代模型反复细化，每轮逐步完善需求逐步清晰、需要持续反馈可能出现范围蔓延
敏捷模型小步快跑、持续交付、响应变化、测试左移需求变化快、团队协作紧密对人员素质和自动化要求高

2.2 软件测试与开发的关系

测试贯穿软件生命周期，与开发阶段一一对应：需求阶段对应验收测试准备，设计阶段对应系统/集成测试准备，编码阶段对应单元测试，交付阶段对应验收测试。测试不是开发完成后的“最后一道工序”，而是与开发并行、持续进行的质量活动。

2.3 测试方法分类

按是否运行程序

静态测试：不运行程序，通过走查、审查、评审、静态分析发现代码/文档缺陷。
动态测试：运行程序，比较实际输出与预期输出。

按是否利用内部结构

白盒：依据程序内部逻辑结构。
黑盒：依据需求规格，只看输入输出。
灰盒：二者结合，既关注接口也关注部分内部结构。

按执行方式

人工测试：依赖人的判断、探索和经验。
自动化测试：工具/脚本执行，适合回归、性能、大量数据。

其他常用分类

功能测试 / 性能测试；回归测试；冒烟测试；验收测试；Alpha / Beta 测试。

易混点

静态/动态是按“是否运行程序”划分；黑盒/白盒/灰盒是按“是否利用程序内部结构信息”划分。两者是不同维度，不能混为一谈。例如静态分析属于白盒；只检查输入输出则属于黑盒。

2.4 五个测试过程模型

（1）V 模型：开发与测试一一对应

需求分析
↔
验收测试
概要设计
↔
系统测试
详细设计
↔
集成测试
编码
↔
单元测试

V 模型的不足：测试被放在编码之后，介入过晚，缺陷到后期才被发现，修复成本高；图中未体现测试与开发的并行关系，容易让人误以为测试只是开发完成后的一个环节。

（2）W 模型：开发一个 V，测试一个 V

开发活动并行的测试活动目的
需求分析需求评审、验收测试准备尽早发现需求缺陷
概要设计设计评审、系统测试准备尽早发现架构与接口问题
详细设计详细设计评审、集成测试准备尽早发现模块设计问题
编码单元测试、代码评审尽早发现代码缺陷

W 相比 V 的改进：测试与开发并行推进；测试对象不仅是程序，还包括需求、设计等文档；文档在编写阶段就被评审和验证，缺陷可以在源头被发现，避免向后续阶段扩散。

（3）H 模型：测试是独立流程

H 模型强调测试是一个独立于开发的流程。只要测试条件具备、测试准备完成，测试就可以开展，不一定要等开发全部结束。其局限是对测试管理和测试人员素质要求较高。

（4）X 模型：片段编码、片段测试、逐步集成

X 模型主张先把各个程序片段分别编码、分别测试，再通过集成逐步构成整体，强调对单个片段的独立验证。

（5）前置测试模型（Pretest）

把测试计划、测试用例设计等活动提前到需求与设计阶段，使开发与测试紧密结合、同步推进，从而尽早发现需求与设计中的问题。

V 模型配对口诀

需—验、概—系、详—集、编—单。需求分析对验收测试，概要设计对系统测试，详细设计对集成测试，编码对单元测试。

3.1 白盒测试是什么

白盒测试又称结构测试，依据程序的内部逻辑结构设计用例，检查语句、判定、条件、路径、循环、数据流等是否正确。白盒测试主要用于单元测试阶段，通常由开发人员或白盒测试人员完成。

静态白盒测试包括：代码走查、正式审查、评审、编码标准与规范检查、通用代码审查清单等。它不运行程序，直接分析代码和文档。

3.2 控制流图与环形复杂度

控制流图（CFG）用节点表示语句或语句块，用有向边表示控制流。绘制时可以把顺序执行的多个语句压缩成一个节点；判定节点通常有两条出边（真、假）；循环用回边表示。

环形复杂度 V(G) 的三种计算方法

V(G) = E − N + 2　（E 为边数，N 为节点数）
V(G) = P + 1　（P 为判定节点数）
V(G) = 区域数　（含图外部区域）
  • 三种方法的结果必须一致，可用于相互校验。
  • V(G) = E − N + 2 只适用于连通流图。
  • V(G) 的物理含义：程序中独立路径的条数，也是覆盖所有语句所需的最少测试用例数，同时是程序逻辑复杂度的度量。
例某程序的控制流图有节点数 N = 9、边数 E = 11、判定节点数 P = 3，区域数为 4（含图外部区域）。请用三种方法分别计算 V(G)，并说明其含义。
查看参考答案与解析

方法一：V(G) = E − N + 2 = 11 − 9 + 2 = 4。

方法二：V(G) = P + 1 = 3 + 1 = 4。

方法三：V(G) = 区域数 = 4。

含义：V(G) 等于程序中独立路径的条数，即为覆盖所有语句所需的最少测试用例数（基本路径集中的独立路径个数），同时也是衡量程序逻辑复杂程度的度量值。三种方法结果一致，可相互校验。

3.3 逻辑覆盖六种准则

准则要求主要目的典型弱点
语句覆盖每条可执行语句至少执行一次让代码都被“走到”最弱，可能漏掉判定中的逻辑错误
判定覆盖（分支覆盖）每个判定的真、假分支各至少执行一次覆盖每个分支不保证每个条件都取到真/假
条件覆盖每个条件取真、取假各至少一次覆盖条件取值不保证每个判定结果都出现
判定/条件覆盖同时满足判定覆盖与条件覆盖兼顾分支与条件不一定覆盖条件组合
条件组合覆盖每个判定内各条件取值的所有组合至少出现一次覆盖判定内部组合组合数随条件数指数增长
路径覆盖覆盖程序中所有可能的执行路径覆盖路径组合路径数随分支指数增长，实际只能选关键路径

强弱顺序（课程口径）

语句覆盖判定覆盖条件覆盖判定/条件覆盖条件组合覆盖路径覆盖
必须补充的一句话

判定覆盖与条件覆盖不是严格的包含关系：条件覆盖不一定满足判定覆盖，判定覆盖也不一定满足条件覆盖，二者侧重点不同。上面的“由弱到强”是教材/本题要求的课程顺序；简答题按此顺序写，同时补一句“二者侧重点不同”更稳妥。

例：判定语句“A > 1 并且 B = 0”

设判定为 if (A > 1 && B == 0)，其内部有一条可执行语句。不同覆盖准则的用例可以这样取：

准则测试数据覆盖情况
语句覆盖(A=2, B=0)判定为真，内部语句执行一次；未覆盖假分支
判定覆盖(2, 0)、(1, 1)判定分别为真、假
条件覆盖(2, 1)、(1, 0)A>1 取真/假，B=0 取假/真；但两次判定都为假，未覆盖真分支
判定/条件覆盖(2, 0)、(1, 1)判定真/假、条件真/假都覆盖
条件组合覆盖(2, 0)、(2, 1)、(1, 0)、(1, 1)两个条件的四种组合全部出现
路径覆盖所有可能路径简单 if 结构中与组合覆盖类似；有循环/多分支时路径数迅速增长
高频问法

若把逻辑运算符“并且”误写成“或者”，只用语句覆盖能否发现？不能。取 A=2、B=0 一个用例即可让判定内的语句执行；无论运算符是“并且”还是“或者”，该用例的执行路径都相同，错误无法暴露。要发现该错误，需要取 A=2、B=1 或 A=1、B=0 这类一个条件真、一个条件假的用例。

3.4 基本路径法

  1. 根据源程序或详细设计画出控制流图。
  2. 计算环形复杂度 V(G)，确定独立路径的条数。
  3. 确定一组基本路径（独立路径）集，使每条路径至少引入一条此前路径未使用的边。
  4. 为每条基本路径设计输入数据并写明预期输出，生成测试用例。
  5. 执行用例并比对结果。

路径条数与用例条数：基本路径集中独立路径的条数等于 V(G)。通常每条独立路径设计一条用例，但用例条数不必机械等于路径数——关键是保证每条独立路径至少被执行一次（即所有语句至少执行一次）。

基本路径法实例：Rectangle 构造函数

构造函数要求长、宽都在 (0, 50) 内；若不在范围内则取默认值 1。两个复合条件被拆成四个判定，因此判定节点数为 4，V(G) = 4 + 1 = 5，需要 5 条基本路径。

路径路径含义输入 (w, h)预期输出 (width, height)
Path 1w 合法、h 合法(10, 20)(10, 20)
Path 2w ≤ 0，h 合法(0, 20)(1, 20)
Path 3w ≥ 50，h 合法(60, 20)(1, 20)
Path 4w 合法，h ≤ 0(10, 0)(10, 1)
Path 5w 合法，h ≥ 50(10, 60)(10, 1)

注意：Path 2 与 Path 3 的预期输出相同，Path 4 与 Path 5 的预期输出相同，但它们经过的路径不同；基本路径法关心的是“路径是否被执行”，不能只看输出是否相同。

3.5 循环测试

对“最多循环 m 次”的简单循环，至少选取以下数据：

0 次（跳过循环）→ 1 次→ 2 次→ m−1 次→ m 次→ m+1 次（越界）→ 很多次（性能）

例如最多循环 10 次：取 0、1、2、9、10、11，以及可行的“很多次”。嵌套循环：从最内层开始，先按简单循环测试内层，并把外层循环次数设为最小值，再逐层向外推进。串接（并列）循环：可分别按简单循环处理。非结构循环：应重新设计为结构化循环后再测试。

3.6 数据流测试

数据流测试关注变量从“定义（def）”到“使用（use）”的路径，即 def-use 关系。若从定义点到使用点存在一条路径，且该路径上变量未被重新定义，则构成一条定义—使用路径（定义-清除路径），应设计用例覆盖这类路径。

它重点检查变量定义与使用是否匹配，想发现的问题包括：变量未定义就被使用、定义之后从未被使用（冗余或漏写）、定义与使用之间被错误重定义等。

4.1 黑盒测试是什么

黑盒测试又称功能测试，把被测软件看成一个“黑盒子”，不关心内部代码结构，只依据需求规格说明书，通过输入与输出检查功能是否正确。黑盒测试主要用于集成测试、系统测试和验收测试阶段。

优点：站在用户视角、无需了解代码、可以尽早开展；缺点：用例可能冗余、难以覆盖内部路径、高度依赖需求文档的质量。

4.2 等价类划分法

把输入域划分成若干互不相交的子集（等价类），同一子集内任取一个数据，对发现缺陷的作用等效。因此每个等价类取一个代表即可，大幅压缩用例数量。

  • 有效等价类：符合需求、合法的输入集合。
  • 无效等价类：不符合需求、非法的输入集合。
  • 设计原则：每个无效等价类至少设计一个用例，且一个用例只覆盖一个无效等价类，避免多个无效条件相互屏蔽。
例某输入框要求用户输入 1 到 100 之间的整数。请划分有效等价类和无效等价类，并分别给出测试数据。
查看参考答案与解析

有效等价类：1 到 100 之间的整数，任取一个代表，如 50。

无效等价类：① 小于 1 的数（如 0）；② 大于 100 的数（如 101）；③ 非整数（如 3.5）；④ 非数字字符（如 abc）；⑤ 输入为空。

每个无效等价类单独设计一条用例，例如：0、101、3.5、abc、空。不要把多个无效条件放在同一条用例里，否则无法判断是哪个条件导致失败。

4.3 边界值分析法

大量缺陷发生在输入或输出范围的边界上，因此要专门取边界点及其两侧的点。三个关键点：

因果图先用“原因（输入条件）”和“结果（输出状态）”画出逻辑关系，再标注约束，最后转换成决策表并生成用例。它特别适合检查多个输入条件的组合情况。

5.1 单元测试

测试对象：单个模块、函数或类。单元测试以白盒测试为主、黑盒测试为辅，通常由开发人员在编码阶段完成。

单元测试的五个任务

  1. 模块接口：参数个数、类型、顺序是否正确，返回值是否正确。
  2. 局部数据结构：变量初始化、类型、越界、指针等问题。
  3. 重要的执行路径：独立路径与关键逻辑分支。
  4. 出错处理路径：异常、错误分支是否正确处理。

6.1 面向对象特性对测试的影响

特性对测试的影响应对思路
封装信息隐藏使对象内部状态不能直接被观察和设置，测试只能通过公开接口间接验证，状态相关错误不易暴露增加只读的状态观察方法；测试时用测试类/友元类读取或设置状态，测试后移除
继承父类缺陷会随继承扩散；子类继承和重定义的方法必须在子类环境中重新测试；父类改动后所有子类都需回归按继承层次组织测试，父类在先、子类在后；父类变更后做回归测试
多态 / 动态绑定同一消息在不同对象上绑定不同实现，实际执行代码要到运行期才能确定，路径组合骤增覆盖所有可能的动态绑定组合；结合类图/对象图分析

结论：这些特性使以函数为单位的传统测试方法不足以覆盖，需要采用类测试、基于服务/状态的测试以及面向对象的集成测试。

6.2 面向对象测试的层次

传统测试面向对象测试测试对象
单元测试类测试 / 对象测试类、对象、成员方法、对象状态
集成测试类簇集成测试类之间的消息传递与协作
系统测试系统测试整个面向对象系统

面向对象系统中，系统的最小可测试单元不再是函数或过程，而是类和对象。类和对象封装了很多方法和属性，提高了聚合度、降低了耦合度，但也牺牲了单元测试的容易性。

6.3 类测试（面向对象的单元测试）

基于服务的测试

把类中的每个成员方法（服务）当作一个单元分别测试，属于类内部的单元测试。可用块分支图（BBD）建模，再按基本路径法设计用例。

基于状态的测试

把对象的状态转换作为测试对象，先画状态转换图（OSD），再设计用例覆盖各状态及其迁移条件与结果。

基于对象的测试

类只有实例化后才能起作用，因此需要测试构造函数、析构函数以及对象的创建与销毁。

基于响应状态的测试

从类和对象的责任出发，以外界向对象发送特定的消息序列来测试对象的响应。

课程重点是“基于服务”和“基于状态”两类；实际中两者结合：先用基于服务的方法验证各方法本身，再用基于状态的方法验证由方法调用序列引起的状态变化。

块分支图（BBD）五元组（了解）

服务 f 的 BBD 可写为 f = (Du, Dd, P, Fe, G)：Du 为引用的全局/类数据，Dd 为修改的数据，P 为参数与返回值，Fe 为被调用的其他服务，G 为块体（控制结构图）。BBD 可由源程序逆向构造，也可在设计阶段构造；后者更可靠。

得到 BBD 后，可将其转换为控制流图，计算 V(G)，用基本路径法设计用例。例如矩形类 Rectangle 的构造函数，四个判定对应 V(G)=5，设计 5 条基本路径用例即可。

基于状态的测试：数组栈

数组栈类含 Push、Pop 方法和属性 Top，状态可分为“正常、空、满”三种。测试用例必须遍历所有状态，并在每个状态中设计非法操作（例如在空状态调用 Pop），以验证健壮性。

状态切换效率问题：若栈空间为 64 KB、每项 1 字节，要把空栈切换到满栈，必须调用 Push 64×1024 次；由于封装，测试无法直接修改属性。解决办法是引入测试类/友元类，直接读取或修改对象属性，实现状态快速切换，测试完成后移除这些辅助成员。

6.4 面向对象的集成测试

面向对象的集成测试主要测试类簇，通常需要在整个程序编译完成后进行。由于面向对象程序具有动态特性，控制流往往无法确定，因此常对整个编译后的程序做基于黑盒的集成测试。

类簇测试的内容

  • 关联和聚合关系：选择主动发送消息的类的测试用例，加载驱动程序运行。
  • 继承关系：子类中继承的方法和重定义的方法必须在子类环境中重新测试。
  • 多态 / 动态绑定：实例变量中的每一种取值应至少在测试用例中出现一次。

两种类集成策略

策略做法特点
基于线程的测试集成对某输入或事件作出回应的相互协作的一组类（一个线程），分别集成并测试每个线程关注一次事件引发的一连串消息；需回归测试保证无副作用
基于使用的测试先测试很少使用其他类的“独立类”，再逐步测试使用独立类的“依赖类”，直到构成完整系统从底层/独立类开始，逐步向外扩展

面向对象集成测试可分两步：先进行静态测试（检查程序结构是否符合设计，如类关系图、调用关系图），再进行动态测试（按覆盖标准设计用例，如服务覆盖、消息线程覆盖、状态覆盖）。

6.5 面向对象的系统测试

面向对象的系统测试是对所有类和主程序构成的整个系统进行的整体测试，以验证软件系统的正确性和性能指标，满足规格说明书和任务书的要求。测试用例可从对象—行为模型和事件流图中导出。

具体内容包括：功能测试、强度测试、性能测试、安全测试、恢复测试、可用性测试、安装/卸载测试等。系统测试应尽量搭建与用户实际使用环境相同的测试平台。

7.1 自动化测试的基本概念

定义：软件测试自动化是通过软件测试工具，按照测试人员预定的计划和测试用例对软件产品进行自动测试；是把以人为驱动的测试行为转化为机器执行的一种过程。

自动化测试的意义

  • 节约时间，提高执行效率。
  • 更可靠，提高精确度和准确度。
  • 有助于立即测试、持续回归。
  • 减轻测试工程师的重复劳动，使其关注更有创造性的任务。
  • 更好地利用全球资源；有些测试（如性能、并发、大量数据）必须自动化。

常用术语与技能类型

术语 / 类型含义
测试包一组测试用例被组合并与一组场景关联
自动化测试框架由基础模块、管理模块、统计模块等组成的工具集合
记录与回放录制键盘/鼠标操作序列，以后按顺序回放；技能要求较低
数据驱动测试脚本与测试数据分离，用数据表驱动同一脚本反复执行
行动（关键字）驱动用户描述操作，框架自动生成并执行所需步骤

7.2 自动化测试框架的组成

外部模块

测试用例数据库（用例、步骤、执行历史）与缺陷库（缺陷详细信息）。

场景与配置

存放自动化中使用的变量，可动态改变以形成不同的执行、输入、输出和状态条件。

测试用例与框架

把“要执行什么”和“如何执行”结合，从用例库提取用例、场景、变量并执行。

工具与结果

调用模拟器/工具；保存每次执行结果、场景和变量值，且不能覆盖历史结果。

报告生成器

提取结果并生成格式化报告与指标。

报告 / 指标库

存储所有报告和指标，供日后分析。

7.3 自动化测试的过程模型

教材三阶段：自动化测试需求分析 → 自动化测试框架搭建 → 产品和自动化测试包的测试。框架搭建要沉淀公用对象、公用环境、公用方法和测试数据。

脚本生命周期四阶段（闭环）：

脚本开发→测试运行→结果分析与报告→脚本维护↺

为什么脚本维护是成败关键：脚本会因软件版本更新、界面控件改变、业务流程调整而大量失效，维护成本往往高于首次开发成本；如果维护跟不上，脚本会成批失效、无法回放，自动化就形同虚设。

7.4 自动化测试的适用场合与选择

前提条件

  • 需求变动不频繁。
  • 项目周期足够长。
  • 自动化测试脚本可重复使用。
  • 被测软件已基本稳定，有成熟可复用的用例，具备工具与人员技能，预期收益（ROI）足够。

适合与不适合

适合

回归测试、文档管理、测试报告生成、覆盖率统计；大量数据驱动、性能测试、并发压力测试；步骤频繁重复、手工难以完成的测试。

不适合

需求频繁变化、功能与界面尚不稳定、只执行一次、需要较强人工判断与探索（探索性测试、易用性测试）的场合。

选择因素：项目影响、实现复杂度、时间、代码/需求稳定性、资源、覆盖率、自动执行能力；同时要分析投入回报，自动化不能完全替代手工测试。

7.6 QTP 的三个核心概念

概念作用一句话
对象库（Object Repository）存放被测对象的属性及逻辑名，脚本依靠它识别并操作界面控件解决“操作谁”
检查点（Checkpoint）在脚本中设置断言，把运行时实际值与期望值比较，判定测试是否通过解决“结果对不对”
参数化（Parameterization）用变量或数据表代替脚本中写死的常量，使同一脚本能用于不同数据与场景解决“一套脚本跑多组数据”

数据驱动测试

原理：把“测试脚本”与“测试数据”分离。脚本只开发一份，其中变化的输入值改成参数，测试数据放在数据表（DataTable）中；运行时脚本循环读取数据表的每一行，用不同数据反复执行同一套操作。

实现要点：① 录制或编写通用脚本，把写死的输入值改为参数；② 在数据表中准备多组数据；③ 设置循环，使脚本逐行取参数并执行；④ 对每行结果设置检查点判定期望输出。

QTP 基本操作流程

  1. 启动 QTP，新建测试并选择被测应用类型。
  2. 录制测试脚本，QTP 自动生成脚本语句并把对象记录到对象库。
  3. 编辑脚本：插入检查点、进行参数化、调整语句逻辑。
  4. 调试脚本（断点、单步），确认无误后运行。
  5. 查看测试结果窗口，分析通过/失败情况及原因，生成测试报告。
关键提醒

录制只是手段，回放必须插入检查点校验预期结果，否则“回放通过”并不代表功能正确。

7.7 LoadRunner 与性能测试

性能测试核心指标

并发用户数
同一时刻向系统发出请求的虚拟用户数量。
响应时间
从发出请求到收到完整响应所经历的时间，含网络传输与服务器处理时间。
吞吐量
单位时间内系统处理的请求数或数据量，如“请求数/秒”“字节/秒”。
TPS
每秒完成的事务数，用于衡量系统处理能力。
资源利用率
CPU、内存、磁盘、网络等资源的使用情况。
思考时间 / 集合点
思考时间模拟用户操作间的停顿；集合点让多个虚拟用户到达该点后同时释放，制造瞬时并发。

指标关系：系统未达到处理极限时，并发用户数增加，吞吐量随之上升而响应时间基本平稳；当达到饱和点后，并发继续增加，吞吐量不再上升甚至下降，响应时间急剧变长。性能测试的目的就是找到这个拐点，确定系统的最佳并发区间与最大处理能力。

LoadRunner 三大组件

组件作用
VuGen（虚拟用户生成器）录制或编写、调试虚拟用户脚本，并完成参数化、关联、事务、检查点等脚本增强
Controller（控制器）设计并运行测试场景，设置虚拟用户数、负载生成器和运行策略，并实时监控
Analysis（分析器）对测试数据进行分析，生成响应时间、吞吐量等图表和测试报告

数据流：VuGen 产出脚本 → Controller 创建场景、施加负载、采集数据 → Analysis 分析并给出结论。顺序可记为“脚本 → 场景 → 分析”。

脚本增强技术

技术解决的问题
参数化把写死的常量替换为参数，模拟不同用户使用不同数据
关联提取服务器动态返回的值（如会话标识）并在后续请求中引用，解决回放失败
事务把一组操作括起来，度量这组业务流程的响应时间
集合点让多个虚拟用户到达该点后同时释放，制造瞬时并发压力
思考时间模拟用户操作间的停顿，使负载更接近真实
检查点校验返回内容是否正确

负载/压力测试步骤

  1. 制定负载测试计划，明确目标与性能指标（并发数、响应时间要求、持续时间等）。
  2. 开发测试脚本，用 VuGen 录制并进行参数化、关联、事务等增强。
  3. 创建运行场景，在 Controller 中设置虚拟用户数、负载生成器、集合点和运行策略。
  4. 运行测试场景并实时监控响应时间、吞吐量、服务器资源利用率等指标。
  5. 分析结果，用 Analysis 查看性能曲线、定位瓶颈，必要时调整参数后重复测试。

10.1 测试计划

定义：测试计划描述了要进行的测试活动的范围、方法、资源和进度，确定测试项、被测特性、测试任务、谁执行任务以及可能的风险。它可以有效预防计划风险，保障计划顺利实施。

测试目标的三类

  • 整体目标：针对整个软件项目或产品确定。
  • 阶段性目标：分别针对单元、集成、系统和验收测试定义期望结果。
  • 特定任务目标：针对某些具体任务确定。

测试计划的主要内容

要素说明
测试目的与目标被测对象、质量目标
测试范围测什么、不测什么，以及进入/退出准则
测试策略与方法测试类型与所用方法
测试资源人员、环境、设备、工具
测试进度与里程碑阶段划分、关键节点
测试交付物与文档计划、用例、报告等
风险与应对措施识别、量化、缓解、跟踪
用例与缺陷管理流程流程、标准、工具

测试策略要回答：在哪些阶段、按什么层次开展测试；采用哪些测试类型（功能、性能、安全、兼容性等）；用黑盒还是白盒、手工还是自动化；回归测试如何组织。

10.2 测试范围分析与工作量估算

范围分析：一般先分析功能测试范围，再分析非功能测试范围。功能范围主要依据软件规格说明书，结合功能之间的逻辑关系和用户使用习惯细化；非功能范围可从性能、兼容性、适用性、安全性等方面分析。

范围管理：理解哪些内容构成发布版本；将发布版本分解为特性；确定特性测试优先级；确定哪些特性测试、哪些不测试；收集数据，准备估计测试资源。

工作量估算

规模度量

代码行数、功能点（FP）、屏幕数/报表数/事务数。

影响规模的因素

被测产品规模、所需自动化范围、要测试的平台与互操作环境数量。

常用估算方法

类比法、专家判断法（Delphi）、按比例估算法、自下而上法（用例数 ÷ 每人日执行数）。

其他影响因素

生产率数据、重用机会、过程健壮性、人员技能、缺陷修复与回归次数。

估算应结合历史数据，并为缺陷修复和回归测试预留缓冲余量。

10.3 资源安排与进度管理

测试角色：测试工程师、测试负责人、测试经理等；健全的测试组可包括测试组长、实验室管理员、自动化测试工程师、资深测试工程师和初级测试工程师。培训分为纵向（知识传递）和横向（跨团队交流）。

两种常用的进度管理方法

方法原理用途
累积缺陷曲线法前期缺陷发现率高，随着时间推移和缺陷修复，发现速率降低；当缺陷越来越难发现时，预示测试进入尾声通过累积缺陷曲线判断测试进度与收敛情况
测试进度 S 曲线法把计划进度与实际进度（测试用例/测试点数量）画成曲线进行比较发现差距、调查原因、纠正偏差

10.4 测试风险控制

风险管理要素：风险确定 → 风险量化 → 风险缓解策划 → 风险应对。风险管理是一个循环，随着一些风险被解决，其他风险又可能出现。

风险量化：用数字描述风险，两个要素是“风险发生的可能性”和“风险影响的程度”。风险指数 = 风险可能性 × 风险影响，常用金额方式表示。

常见风险

  • 需求不明确或频繁变更。
  • 进度依赖、开发延迟导致测试时间不足。
  • 测试环境或测试数据不具备。
  • 人员技能不足或人员流动。
  • 缺陷修复不及时导致回归延误。
  • 出现“影响测试继续进行”的缺陷。
  • 不能获得自动化测试工具。

应对手段：测试尽早介入、提前设计并评审用例、按缺陷集群性把资源优先投向关键与高风险模块、预留进度缓冲、定期状态评审与进度跟踪。

10.5 测试报告与测试评估

三类测试报告

报告内容
测试事件报告测试周期内遇到缺陷时的沟通，是缺陷库中的一条记录，每个缺陷有唯一标识
测试周期报告本周期完成的活动、发现的缺陷及严重性分类、缺陷修复进展、未修改的严重缺陷、进度与工作量偏差
测试总结报告对测试周期结果进行总结，为纠正质量问题提供依据，为验收和交付打基础；给出测试和产品质量的结论

测试报告的主要内容：测试概述（目的、范围、被测对象与环境）、测试执行情况（用例总数、执行数、通过/失败数、进度）、缺陷统计与分析（按严重程度、模块、类型分布）、遗留问题与风险说明、测试结论与建议。

测试报告与测试评估的区别与联系：报告记录并呈现测试活动的过程、结果与数据，面向事实与过程；评估对测试对象的质量以及测试活动本身的效果作出判断和结论，面向结论与决策。评估以报告提供的数据为依据，报告是评估的输入。

10.6 覆盖率与缺陷度量（计算重点）

覆盖率

覆盖率 = 至少被执行一次的 item 数 ÷ item 总数
  • 基于需求的测试覆盖：在测试生命周期中多次评测，并在里程碑处提供“已计划、已实施、已执行、成功”的覆盖标识。
  • 基于代码的测试覆盖：评测已执行代码的多少，与之相对的是剩余未执行代码的多少。
重要提醒

代码覆盖率达到 100% 也不能代表测试覆盖率很高：代码可能没有实现需求中定义的功能，或者实现的功能与用户需求不符，这类问题很难通过代码覆盖率发现。

缺陷度量四指标

缺陷发现率
把发现的缺陷数量作为时间的函数来评估，创建缺陷趋势图。
缺陷潜伏期
缺陷处于特定状态下的时间长短；发现越晚，损害越大、修复成本越高。
缺陷分布（密度）
缺陷在软件规模上的分布，如每千行代码或每个功能点的缺陷数。
整体缺陷清除率
开发过程中发现的缺陷占发现的总缺陷的比例，越高说明质量越好。
缺陷密度 = 缺陷数量 ÷ 代码行数（或功能点数）
设 F 为功能点，D1 为开发过程中发现的缺陷数，D2 为发布后发现的缺陷数，D = D1 + D2
质量 = D2 / F　缺陷注入率 = D / F　整体缺陷清除率 = D1 / D
例某软件项目有 100 个功能点，开发过程中发现 15 个错误，提交后又发现 5 个错误。请计算质量、缺陷注入率和整体缺陷清除率。
查看参考答案与解析

已知 F = 100，D1 = 15，D2 = 5，D = D1 + D2 = 20。

质量 = D2 / F = 5 / 100 = 0.05 = 5%。

缺陷注入率 = D / F = 20 / 100 = 0.2 = 20%。

整体缺陷清除率 = D1 / D = 15 / 20 = 0.75 = 75%。

整体缺陷清除率越高，软件产品的质量越好；否则清除率越低，质量越差。

11.2 软件质量保证（SQA）

SQA 定义：建立一套有计划、有系统的方法，来向管理层保证拟定出的标准、步骤、实践和方法能够正确地被所有项目采用。其目的是使软件过程对于管理人员来说是可见的；它通过对软件产品和活动进行评审和审计来验证软件是否合乎标准。

  1. 软件质量保证工作是有计划进行的。
  2. 客观地验证软件项目产品和工作是否遵循恰当的标准、步骤和需求。
  3. 将软件质量保证工作及结果通知给相关组别和个人。
  4. 高级管理层接触到在项目内部不能解决的不符合类问题。
  5. 软件质量需要全面的测试工作来保证。

全过程

全员

METHODS

解题模板：大题按这个顺序写

考试大题不是“想到哪写到哪”。下面 8 个模板覆盖最常见的用例设计、计算和简答题。做题时先判断题型，再套模板，最后补一句结论。

模板 1　等价类划分 + 边界值

适用：输入框、号码、金额、长度、日期等“有范围、有格式”的题。

  1. 从需求中找出所有输入项，并写出每个输入项的合法规则。
  2. 对每个输入项划分有效等价类和无效等价类，分别编号。
  3. 取边界：上点（边界上的点）、离点（紧邻边界的点）、内点（区间内部任意点）。
  4. 设计用例：有效等价类可以合并；每个无效等价类单独一条用例。
  5. 每条用例写清“输入 + 覆盖的等价类/边界 + 预期输出”。
阅卷点

① 有效/无效分清楚；② 无效用例不合并；③ 边界值有上点、离点、内点；④ 每条都有预期输出；⑤ 最后说明“这样能用较少用例覆盖主要输入空间”。

模板 2　逻辑覆盖

适用：给一段含 if / while 的程序，要求“分别按语句、判定、条件、判定/条件、条件组合、路径覆盖设计用例”。

  1. 把复合判定拆成单个条件，列出条件与判定的关系。
  2. 画一张小表：条件取值组合 → 判定结果 → 执行语句/路径。
  3. 按题目要求的覆盖准则挑选数据；能覆盖多个准则的用例可以复用。
  4. 逐条写“输入 → 预期输出 → 覆盖了哪些语句/分支/条件/路径”。
  5. 若题目问“某错误能否发现”，说明该错误需要哪类用例才能暴露。
准则选取思路常见失分
语句覆盖让每条可执行语句至少走一次只走真分支，漏掉 else
判定覆盖每个判定真、假各一次把“条件”当成“判定”
条件覆盖每个条件真、假各一次忽略判定结果可能仍为同一个
判定/条件覆盖同时满足上面两者只满足其中一个
条件组合覆盖每个判定内所有条件组合都出现漏组合，尤其 2 个条件要 4 组
路径覆盖覆盖所有可能执行路径把“独立路径”当成“所有路径”

模板 3　基本路径法

  1. 画控制流图：顺序语句可合并，判定有真/假两条出边，循环有回边。
  2. 算 V(G)：E − N + 2、P + 1、区域数，三选一并写出。
  3. 列基本路径集：条数 = V(G)；每条新路径至少引入一条此前未用的边。
  4. 为每条路径设计输入数据，写预期输出。
  5. 检查：是否所有语句至少执行一次；是否覆盖所有判定分支。
两个高频坑

① 复合条件在基本路径法里通常要拆成单个判定，拆完后判定节点数会增加，V(G) 也会变；② 不同路径可能得到相同输出，不能因为输出相同就认为路径重复。

模板 4　决策表

  1. 列条件桩（所有条件）和动作桩（所有动作）。
  2. 列出条件的所有取值组合：n 个二值条件有 2n 列。
  3. 为每一列填动作项，确定该组合下执行哪些动作。
  4. 合并结果相同的规则，化简决策表。
  5. 每条规则（每一列）对应一条测试用例，写输入与预期输出。

决策表适合“多个条件组合决定多个动作”的题，如折扣、权限、计费、告警。条件越多，表越大，所以化简很关键。

模板 5　因果图

  1. 把输入条件标为“原因”，把输出结果标为“结果”。
  2. 画出原因与结果之间的逻辑关系（与、或、非）。
  3. 标注约束：E、I、O、R 为输入约束，M 为输出约束。
  4. 把因果图转换成决策表。
  5. 由决策表每一列生成测试用例。
约束含义一句话
E（Exclusive，异）a、b 最多一个为 1，不能同时为 1不能同时发生
I（Inclusive，或）a、b、c 至少一个为 1，不能同时为 0至少要有一个
O（One and only one，唯一）a、b 有且仅有一个为 1必须有一个，且只有一个
R（Requires，要求）a 为 1 时 b 必须为 1有 a 就必须有 b
M（Mask，屏蔽）a 为 1 时 b 被强制为 0a 出现则 b 被屏蔽

模板 7　覆盖率与缺陷度量计算

覆盖率 = 至少被执行一次的 item 数 ÷ item 总数
缺陷密度 = 缺陷数量 ÷ 代码行数（KLOC）或功能点（FP）
D = D1 + D2　（D1 开发中发现，D2 发布后发现）
质量 = D2 / F　　缺陷注入率 = D / F　　整体缺陷清除率 = D1 / D
  1. 先写公式，再代入数据，最后写单位或百分比。
  2. 百分数要写清分母是谁，不要把“执行率”和“通过率”混在一起。
  3. 最后解释含义：清除率越高，说明开发阶段发现的缺陷占比越大，质量越好。
教材口径提醒

课件例题中“缺陷注入率 = 20/100 = 0.2（2%）”的括号百分比写错了，0.2 应为 20%。考试按公式计算，写 20%。

模板 8　简答 / 对比题

“是什么”型

定义 → 目的 → 组成/分类 → 一个例子 → 一句结论。

“比较 X 与 Y”型

按四个维度写：依据、对象、时机、方法；最后写“二者互补，不能相互替代”。

“为什么”型

先给结论 → 2～4 条理由 → 反例或后果 → 改进办法。

“如何做”型

按流程分步：计划 → 分析 → 设计 → 执行 → 评估 → 报告。

通用收尾句

“因此，实际项目应根据需求、风险和资源选择合适的方法，并与其它方法结合使用，不能相互替代。”

选择：自底向上集成。理由：底层模块先被集成和测试，可以在早期验证底层接口与基础功能，正好对应“底层接口不稳定、需要尽早验证”的需求；代价是需要额外开发驱动模块（Driver）来模拟上层调用。

与其他策略比较：

  • 大爆炸：所有模块一次集成，工作量小、成本低，但缺陷定位困难，适合模块少、风险可控的小系统。
  • 自顶向下：从主控模块开始，需开发桩模块（Stub），能尽早验证上层逻辑与主要控制流，但底层功能验证偏晚。
  • 三明治：自顶向下与自底向上结合，兼顾上下层，可减少桩和驱动的工作量，但中间层模块测试相对滞后。

结论：选用时应综合缺陷定位难度、桩/驱动工作量、进度安排和风险大小决定；本题的关键信号是“底层接口不稳定”，因此优先自底向上。

例 6　缺陷度量计算

题目某项目有 100 个功能点，开发过程中发现 15 个缺陷，发布后又发现 5 个缺陷。求质量、缺陷注入率、整体缺陷清除率，并说明含义。
查看参考答案与解析

已知 F = 100，D1 = 15，D2 = 5，D = D1 + D2 = 20。

  • 质量 = D2 / F = 5 / 100 = 0.05 = 5%。
  • 缺陷注入率 = D / F = 20 / 100 = 0.2 = 20%。
  • 整体缺陷清除率 = D1 / D = 15 / 20 = 0.75 = 75%。

含义：整体缺陷清除率表示开发过程中发现的缺陷占全部缺陷的比例；75% 说明还有 25% 的缺陷漏到发布后。清除率越高，说明缺陷越早被发现和修复，产品质量越好。

课件把 0.2 写成“2%”，是笔误；按公式应为 20%。考试写 20%，并保留计算过程。

例 7　面向对象：银行账户类

题目某“银行账户”类含存入 deposit 和取出 withdraw 两个方法，余额有“正常”和“透支”两种状态。请说明基于服务的测试与基于状态的测试应如何进行。
查看参考答案与解析

基于服务的测试：把每个成员方法当作一个单元分别测试。

  • deposit：正常金额、0、负数、极大金额；检查余额是否正确累加，非法金额是否被拒绝。
  • withdraw：正常取出、恰好取完、超额取出、0、负数；检查余额变化与错误提示。
  • 边界：余额为 0 时取 1 元；余额等于取款额；余额比取款额少 1 元。

基于状态的测试：把对象看成一个有限状态自动机，先画状态转换图，再覆盖状态与迁移。

  • 正常状态：取款额 ≤ 余额 → 仍为正常状态，余额减少。
  • 正常 → 透支：取款额 > 余额 → 进入透支状态（若业务允许），余额为负。
  • 透支 → 正常：存入金额足以补足欠款 → 回到正常状态。
  • 透支状态再取款：按业务规则拒绝或继续透支，预期输出必须明确。

结论：先用基于服务的方法验证各方法本身，再用基于状态的方法验证“方法调用序列”引起的状态变化；两者结合，才能覆盖类的行为。

一、必背公式（计算题先写公式，再代数）

指标公式说明 / 易错点
环形复杂度V(G) = E − N + 2 = P + 1 = 区域数E 边数、N 节点数、P 判定节点数；三种算法必须一致，可互相校验；仅适用于连通流图。
语句覆盖率被执行语句数 ÷ 语句总数 × 100%判定覆盖率同理，按“已执行分支 ÷ 全部分支”计算。
缺陷密度缺陷数 ÷ KLOC（或功能点）注意单位统一，千行代码写作 KLOC。
缺陷注入率D ÷ FD 为开发期 + 发布后发现缺陷总数，F 为功能点/规模；课件中 D/F=20/100=0.2，即 20%。
整体缺陷清除率D1 ÷ DD1 为发布前发现并修复的缺陷数；数值越高，交付质量越好。
质量D2 ÷ FD2 为发布后发现的缺陷数；D = D1 + D2。
测试工作量用例总数 ÷ 每人日执行用例数得到人日数；也可用测试场景数、配置数估算。
风险指数风险可能性 × 风险影响用乘积把风险量化，便于排序和确定缓解优先级。

二、必背清单（考前一晚过一遍）

1. 测试七原则

① 测试显示缺陷存在，不能证明缺陷不存在；② 穷尽测试不可能；③ 测试尽早介入；④ 缺陷集群性（二八原则）；⑤ 杀虫剂悖论；⑥ 测试活动依赖上下文；⑦ 不存在缺陷的谬论。

2. 逻辑覆盖六准则（弱 → 强）

语句 → 判定 → 条件 → 判定/条件 → 条件组合 → 路径。注意：判定覆盖与条件覆盖不是严格包含关系，二者侧重点不同。

3. 因果图五约束

E 互斥（最多一个为 1）、I 包含（至少一个为 1）、O 唯一（有且仅有一个为 1）、R 要求（a=1 则 b 必须为 1）、M 屏蔽（a=1 则 b 强制为 0）。E/I/O/R 是输入约束，M 是输出约束。

4. 四种集成策略

大爆炸（一次性集成，定位难）、自顶向下（需桩 Stub，上层验证早）、自底向上（需驱动 Driver，底层验证早）、三明治（上下结合，中间层滞后）。

5. 单元测试五任务

模块接口、局部数据结构、独立执行路径、错误处理路径、边界条件。Driver 模拟上层调用，Stub 模拟下层被调。

6. 测试过程模型

V 模型（开发与测试一一对应，测试介入晚）、W 模型（双 V、测试与开发并行）、H 模型（测试独立流程，可尽早开展）、X 模型（分段编码分段测试再集成）、前置测试模型（测试计划与用例设计提前）。

7. CMM 五级

初始级 → 可重复级 → 已定义级 → 已管理级 → 优化级，共 18 个关键过程域（KPA）。口诀：初可定管优。

8. ISO 9126 六特性

功能性、可靠性、易用性、效率、可维护性、可移植性。口诀：功可易效维移。

9. IEEE 829 八文档

测试计划、测试设计说明、测试用例说明、测试规程说明、测试项传递报告、测试日志、测试事件报告、测试总结报告。口诀：计设用规，传日事总。

10. 手机测试六技术

释放测试、系统测试、部分测试、焦点测试、压力测试、自由测试。手机测试特殊性：多机型、多网络、多中断。
